# 連携版の設計（別々の mtls-manager で管理するサーバ間の mTLS）

[English](../en/federation-design.md)

> **状態: 設計案（未実装）**。この文書の内容は、確認を経てから段階的に実装します（[15.](#15-実装の段階)）。
> 実装の前に決めること（[16.](#16-決めること)）があります。

## 1. 目的と範囲

これまでの mtls_manager は、**1 つの mtls-ca（1 つのルート CA）**で、連携するサーバをすべて管理する前提でした。
A サーバも B サーバも同じ CA から証明書を取り、同じルート CA を信頼し、相手の名前を許可リスト（`AllowedPeers`）で確かめます。

連携版では、次の構成を扱えるようにします。

- A サーバは **A 側の mtls-ca**（ルート CA A）、B サーバは **B 側の mtls-ca**（ルート CA B）で管理する
- A と B は別のネットワークにあり、それぞれの mtls-ca は相手のサーバに証明書を発行しない（発行できない）
- A サーバと B サーバが、互いの証明書を検証して mTLS でつながる

この文書は、そのための**信頼の結び方（連携）**、その手順、配布、検証、停止の方法を定めます。

範囲外: 3 者以上の連携の網（各組が個別に連携すれば構成できる）、公開の認証局との連携、アプリ間の通信の経路（VPN・専用線など）の設計。

## 2. 前提

- **A と B は別組織（別会社）である**ことを前提に、厳しい方で設計します（決定済み）。この前提の設計は、同じ社内の別ネットワークにもそのまま使えます。相手の CA は「自分たちの管理下にない」ものとして扱います。
  同じ社内の別ネットワークの場合に簡略化できる点は、各節の「社内の場合」に書きます。
- **A と B は別のドメインを使う**（例: A は `a.example.com`、B は `b.example.net`）。重なる場合は連携できません（[6-3.](#6-3-範囲の条件重ならないこと広すぎないこと)）。
- A サーバと B サーバの間で、アプリの通信（mTLS）が届くこと。**CA 同士の通信は必須ではありません**（初回の連携は手作業でできる）。
- 各組織の内部の構成（ルート CA はオフライン、中間 CA に名前制約、証明書は 24 時間など）は、これまでどおりです。

> **社内の場合の別案**: 同じ組織なら、連携ではなく「**ルート CA を共有し、ネットワークごとに中間 CA を立てる**」方が簡単です。
> ルート CA はオフラインなので共有しても危険は増えず、各中間 CA の名前制約で各ネットワークの名前の範囲を分けられます。
> 各サーバは同じルート CA を信頼するだけで済み、連携の手順・配布はいりません。今の実装のままでも構成できます
> （中間 CA を 2 つ作り、それぞれの mtls-ca に持たせる）。連携版が要るのは、**ルート CA を共有できない**（別組織、または管理の境界を分けたい）場合です。

## 3. 用語

| 用語 | 意味 |
| --- | --- |
| 連携（フェデレーション） | 2 つの mtls-ca の間で、相手のルート CA を範囲付きで信頼し合う取り決め |
| 連携先 | 連携した相手の組織（とその mtls-ca） |
| 範囲（スコープ） | 連携先のルート CA について、受け入れる証明書の名前の範囲（例: `b.example.net` とそのサブドメイン） |
| 連携情報 | 連携先ごとの「ルート CA の証明書・範囲・状態」の組 |
| トラストバンドル | 承認済みの連携情報（連携先のルート CA と範囲）をまとめたもの。mtls-ca が各サーバへ配る。自分のルート CA と範囲は、バンドルからは取らない（[6-4.](#6-4-自分のルート-ca-と範囲はバンドルから取らない)） |
| 指紋 | ルート CA の証明書の SHA-256（DER のハッシュ）。目で突き合わせて同一性を確かめる |

## 4. 要件

### 4-1. 機能

| # | 要件 |
| --- | --- |
| F-1 | 自分の連携情報（ルート CA の証明書・指紋・自分の範囲・連絡先）を書き出せる |
| F-2 | 連携先の連携情報を取り込み、指紋を照合し、範囲を決めて承認できる |
| F-3 | 承認した連携情報は、各サーバ（mtls-agent）へ自動で配られる |
| F-4 | 各サーバのアプリ（`mtls` ライブラリ）は、連携先の証明書を**その範囲の名前に限って**受け入れる |
| F-5 | 連携を停止（取り消し）でき、各サーバへすぐ反映される |
| F-6 | 連携先のルート CA の入れ替えに、連携を切らずに追従できる |
| F-7 | 連携の追加・承認・停止は、すべて監査ログに残る |

### 4-2. セキュリティ

| # | 要件 |
| --- | --- |
| S-1 | 連携先の CA が、**自分の組織の名前**（自分の `allowed_domains`）の証明書を作っても、受け入れない |
| S-2 | 連携先の CA が、承認した範囲の外の名前の証明書を作っても、受け入れない |
| S-3 | 初回の取り込みで、ルート CA がすり替えられていないことを、通信経路に頼らずに確かめられる |
| S-4 | 連携の承認は、1 人の管理者の判断だけで成立しない（2 人の承認。社内の場合は 1 人でも可にできる） |
| S-5 | 連携先の秘密（鍵）は一切受け取らない。自分の秘密（鍵）も一切渡さない |
| S-6 | 古い・改ざんされたトラストバンドルを、サーバが使い続けない |
| S-7 | CA サーバ（オンライン）が乗っ取られても、**自分の組織の名前**を他の CA に信頼させることはできない（被害は、これまでどおり中間 CA の名前制約の範囲と、連携先の追加にとどまる） |

### 4-3. 非機能

- 連携先が増えても（目安: 数十）、接続ごとの検証の負荷がほぼ変わらない
- CA 同士が通信できない環境でも、手作業だけで運用できる
- 既存の構成（連携なし）は、設定を変えずにこれまでどおり動く

## 5. 全体の構成

```
        組織 A                                              組織 B
┌──────────────────────────┐                    ┌──────────────────────────┐
│ ルート CA A（オフライン） │                    │ ルート CA B（オフライン） │
│        │                 │                    │        │                 │
│  mtls-ca A ── 連携情報 B │ ◀── ① 交換・照合 ──▶ │ 連携情報 A ── mtls-ca B  │
│   │  （範囲: b.example.net）│  （指紋は別の経路で）  │（範囲: a.example.com）│   │
│   │ ② トラストバンドル   │                    │   ② トラストバンドル │   │
│   ▼                      │                    │                      ▼   │
│ mtls-agent（A1, A2…）    │                    │    mtls-agent（B1, B2…） │
│   │ 証明書 + バンドル    │                    │    証明書 + バンドル │   │
│   ▼                      │                    │                      ▼   │
│ アプリ A1 ◀═════════════ ③ mTLS（範囲付きで検証）═════════════▶ アプリ B1 │
└──────────────────────────┘                    └──────────────────────────┘
```

1. 管理者どうしが連携情報を交換し、指紋を別の経路で照合して、範囲を決めて承認する（[7.](#7-初回の連携の手順)）
2. 各 mtls-ca は、トラストバンドルを自分の mtls-agent へ配る（[8.](#8-トラストバンドルの配布)）
3. アプリは、自分のルート CA か、連携先のルート CA（その範囲の名前に限る）につながる証明書を受け入れる（[9.](#9-接続時の検証)）

各サーバの証明書の発行は、これまでどおり自分の組織の mtls-ca だけが行います。

## 6. 信頼のモデル

### 6-1. 交換するもの・しないもの

| 交換する | 交換しない |
| --- | --- |
| ルート CA の証明書（公開情報） | 秘密鍵（ルート・中間・サーバ）、EAB 鍵、HMAC |
| 指紋（別の経路での照合用） | 各サーバの証明書・公開鍵 |
| 自分の範囲（使うドメイン） | 設定ファイル、データベース |
| 連絡先（承認者・緊急連絡） | |

**各サーバの公開鍵は交換しません。** 証明書は 24 時間ごとに鍵ごと入れ替わるため、公開鍵を固定すると毎日交換し直すことになり、
自動更新と両立しないからです。代わりに「相手のルート CA」と「相手のサーバの名前」を承認します。
相手の CA が正しく発行した、許可した名前の証明書だけが通るので、「相手のサーバの公開鍵を承認する」と同じ効果になり、鍵の入れ替えにも自動で追従します。

### 6-2. 範囲付きの信頼

連携先のルート CA を、単に「信頼するルート」に加えるだけでは足りません。相手の CA は、技術的にはどんな名前の証明書でも作れます
（相手の中間 CA の名前制約は相手が付けるもので、こちらからは強制できない）。そのため、**受け入れる側で範囲を確かめます**。

- 連携情報ごとに範囲（ドメインの一覧）を持つ。例: 連携先 B → `b.example.net`
- 接続を検証するとき、相手の証明書が**どのルート CA につながったか**を見て、そのルートの範囲に**証明書の名前がすべて**入っていることを確かめる
- 範囲の外の名前を 1 つでも含む証明書は拒否する（S-1・S-2）
- そのうえで、これまでどおり `AllowedPeers` で相手の名前を限る（範囲は「その CA に任せてよい名前」、`AllowedPeers` は「このアプリが話してよい相手」）

自分のルート CA の範囲は、自分の `policy.allowed_domains` です（その持ち方は [6-4.](#6-4-自分のルート-ca-と範囲はバンドルから取らない)）。

#### 受け入れる証明書の形

連携先の CA は「自分たちの管理下にない」ので、自分の CA が作らない形の証明書も届き得ます。連携先のルートにつながる証明書は、
次の**すべて**を満たすものだけを受け入れます。

- DNS 名（SAN の dNSName）が **1 つ以上**ある（DNS 名が 0 個の証明書は、「すべての名前が範囲に入る」を空の条件で満たしてしまうため）
- DNS 名に**ワイルドカード（`*.`）を含まない**（`*.b.example.net` の証明書 1 枚で、`AllowedPeers` の `*.b.example.net` に一致するどの名前にもなりすませるため）
- DNS 名**以外の SAN**（IP アドレス・URI・メールアドレス）を含まない（範囲は DNS 名でしか表せないため）
- 1 枚の証明書が複数のチェーン（複数のルート）につながる場合は、検証できたチェーンの**いずれか**で、そのルートの範囲に全部の名前が入れば受け入れる
  （各チェーンは、それぞれ独立に正しい信頼の経路であるため）

### 6-3. 範囲の条件（重ならないこと・広すぎないこと）

承認の時点で、次を確かめて満たさなければ承認しません。

- 連携先の範囲が、自分の `policy.allowed_domains` と重ならない（重なると S-1 が守れない）
- 連携先の範囲が、他の連携先の範囲と重ならない（どちらの CA の責任か分からなくなる）
- 範囲が**広すぎない**: 2 ラベル以上のドメインであること（`net` は不可）、パブリックサフィックス（`co.jp`・`com` など）でないこと。
  パブリックサフィックスの一覧は同梱し、承認の画面では範囲の広さ（ラベルの数）を目立たせる

範囲は、相手が申告した範囲（連携情報に含まれる）を上限として、**自分の側で狭めて**承認できます（例: 相手の申告は `b.example.net`、承認は `api.b.example.net` だけ）。

重なりの確認は承認の時点だけでなく、**mtls-ca の起動時**と**バンドルを作るたび**にも行います。承認の後に自分の `policy.allowed_domains` を広げて
既存の連携先と重なった場合は、その連携先をバンドルに入れず、管理画面とログで警告します。さらに、受け入れる側の `mtls` ライブラリでも
重なりを確かめます（[6-4.](#6-4-自分のルート-ca-と範囲はバンドルから取らない)）。

### 6-4. 自分のルート CA と範囲はバンドルから取らない

トラストバンドルは、オンラインの CA サーバ（中間 CA の鍵）が作って署名します。CA サーバが乗っ取られると、攻撃者は好きな内容のバンドルに署名して
配れます。そこで、**バンドルで変えられるのは「連携先の信頼」だけ**にし、自分の組織の信頼はバンドルに頼らないようにします（S-7）。

- 自分のルート CA は、これまでどおり `CAFile`（mtls-agent の `ca_root` / `output.ca`）から読む。バンドルには参照用に**自分のルートの指紋の一覧**
  （ルートの入れ替え中は新旧の 2 つ）を載せ、**その指紋がすべて `CAFile` のルートに含まれる**ことを確かめる（一覧が空、または `CAFile` に無い指紋が
  あれば、**バンドル全体を拒否**する）。「含まれる」で判定するのは、ルートの入れ替えで各サーバの `ca_root` を先に新旧にしておけば、
  入れ替えの途中でも連携が切れないようにするため（入れ替えの順序は、実装時に運用ガイドの「ルート CA を入れ替える」に加える）
- 自分の範囲（`OwnDomains`）は、**自分の中間 CA の名前制約**（`PermittedDNSDomains`）から得る。中間 CA の証明書はオフラインのルートが署名しているので、
  オンラインの CA サーバでは書き換えられない。中間 CA の証明書は、`CAFile` のルートで検証してから使う（自分の証明書の fullchain に含まれている）
  - ローカルの設定（人が書く値）で**狭める**ことだけは認める（名前制約より広い値は使わない）
  - **CA の応答（バンドル・ディレクトリ・その他の API）からは取らない**
  - 範囲が得られない（中間 CA に名前制約が無い、または空）ときは、**連携先を 1 つも信頼しない**（エラーのログを出す）。
    名前制約の無い中間 CA（`mtlsctl intermediate csr -no-name-constraints`）では、連携版は使えない
- `mtls` ライブラリは、連携先の範囲が自分の範囲と**重なる連携先を拒否**する（バンドルの中のその連携先だけを外し、エラーのログを出す）。
  CA の処理（6-3）だけに頼らない
- それでも、乗っ取られた CA サーバは「連携先」を追加できます（自分の範囲と重ならない名前に限る）。これは段階 1 では防げないので、
  [13.](#13-脅威と対策) と、実装時の `security.md` の「守れないこと」に明記します。承認の結果に、オフラインの鍵や承認者の鍵での署名を求める方式は、
  [16.](#16-決めること) で検討します

## 7. 初回の連携の手順

### 7-1. 連携情報を書き出す（両方の組織）

管理画面の「連携」画面（または `mtlsctl federation export`）で、自分の連携情報を書き出します。

```json
{
  "format": "mtls-manager-federation/v1",
  "organization": "Example A Corp.",
  "root_cert": "-----BEGIN CERTIFICATE-----\n...",
  "root_sha256": "3F:9A:...:C2",
  "domains": ["a.example.com"],
  "contacts": ["security@a.example.com"],
  "created_at": "2026-11-01T00:00:00Z"
}
```

秘密情報は含みません。メールやファイル共有で渡してかまいません（すり替えは 7-3 の照合で見つけます）。

`organization` と `contacts` は**相手の申告**で、ファイルと一緒にすり替えられ得ます。表示と連絡の参考にするだけで、**指紋の照合の相手には使いません**（7-3）。

### 7-2. 取り込む

連携先から受け取ったファイルを、管理画面（`admin.operators` の管理者）または `mtlsctl federation import` で取り込みます。
この時点では**承認待ち**で、トラストバンドルには入りません。取り込むと、mtls-ca は次を確かめます。

- 証明書がルート CA として正しい（自己署名、CA:TRUE、期限内、鍵の種類と長さ）
- `root_sha256` が証明書の内容と一致する
- 申告された範囲が 6-3 の条件を満たす

管理画面では、取り込んだ `organization` / `contacts` を「**未検証（相手の申告）**」と表示します。

### 7-3. 指紋を照合する（別の経路で）

画面に表示される指紋を、連携先の担当者と**ファイルを受け取ったのとは別の経路**で突き合わせます。

- **照合の相手は、ファイルとは無関係に、前もって知っている連絡先**とする（契約書に記載の窓口、既存の取引の担当者など）。
  取り込んだファイルの `contacts` は使わない。ファイルをすり替えた攻撃者は、連絡先も自分のものにすり替えられるため
- 例: 電話・ビデオ会議で読み上げる、対面で確認する、双方の署名入りの文書（契約の添付など）に記載する
- 指紋は 32 バイト（64 桁の 16 進）。画面では 4 桁ずつ区切って表示し、読み上げやすくする。**全体（64 桁）を読み合わせる**（一部だけの照合は、
  その部分だけが一致する偽の証明書を作られ得る）
- SSH の初回接続でホストの指紋を確かめるのと同じ考え方です。経路そのものを信頼する必要はありません。ただし、照合する相手を自分で知っていることが前提です

**このため、交換に「信頼できるネットワーク」は必須ではありません。** ルート CA の証明書は公開情報で、守るべきは
「すり替えられていないこと（完全性）」だけだからです。完全性は、別の経路で照合した指紋で確かめます。

### 7-4. 承認する（2 人）

1. 1 人目の管理者が、照合のときに読み上げを聞いて、**指紋の全体（64 桁）を入力**する（貼り付けはできない入力欄にする）。
   あわせて「**照合した相手と経路**」（例: 「契約書記載の○○部 △△ 氏、電話」）を入力し、範囲（必要なら狭める）と有効期限を決めて「承認を申請」する
2. **別の**管理者が内容を確認して「承認」する（同じ管理者は承認できない）
3. 承認されると、連携情報は「有効」になり、トラストバンドルに入る

- 社内の場合: 設定（`federation.require_two_approvals: false`）で 1 人の承認にできる
- 申請・承認・却下は、すべて監査ログ（管理者の名前・連携先・指紋・範囲・照合した相手と経路）に残す
- 有効期限（既定 1 年）を付け、期限の 30 日前から管理画面とログで警告する。更新は 7-3・7-4 のやり直し（再照合）

### 7-5. 相手側も同じ手順を行う

連携は**双方向に別々**です。A が B を承認し、B が A を承認して、初めて双方向の mTLS が通ります
（片方だけの承認では、どちら向きの接続も通りません。mTLS では、サーバとクライアントの双方が相手の証明書を検証するためです）。

## 8. トラストバンドルの配布

### 8-1. mtls-ca → mtls-agent

- mtls-ca は、トラストバンドル（有効な連携情報。参照用に自分のルートの指紋の一覧）を、ACME と同じポートの `GET /federation/bundle` で提供する
- 内容は公開情報だが、**完全性が要る**ので、mtls-agent は既存の CA への接続（自分のルート CA で検証する TLS）でだけ取得する
- バンドルには**エポック・連番・発行時刻・有効期限（既定 2 日）**を付け、中間 CA の鍵で署名する（JWS）。mtls-agent は署名を確かめ、
  古いバンドルの再送を受け入れない（S-6）
  - **エポック**は、mtls-ca のデータの初期化とバックアップからの復旧のたびに変わる乱数の ID。**連番**は、同じエポックの中で単調に増える
  - 同じエポックなら、連番が戻るものは拒否する
  - エポックが変わったバンドルは、署名が正しく、**発行時刻が手元のバンドルより新しい**ときだけ受け入れ、ログに残す
    （CA を復旧すると連番が戻るため、連番だけで比べると全サーバが新しいバンドルを拒否し、停止も届かなくなる）
  - 復旧の手順（運用設計ガイドの「バックアップと復旧」）には、実装時に「復旧したら mtls-ca がエポックを変える（自動）。各サーバが新しいバンドルを
    受け取ったことをログで確かめる」を加える
- mtls-agent は `renew.check_interval`（既定 1 分）ごとに、変化があるか（ETag）を確かめる。CA が止まっていても、
  手元のバンドルは有効期限まで使い続ける（CA の短い停止で連携が切れないように）。期限の 1 日前から警告をログに出す
- 有効期限（既定 2 日）は、「**CA が止まっても連携が続く期間**」であり、同時に「**停止が届かないときの最悪の期間**」でもある（10.）。
  短いほど停止がすぐ確実に効き、長いほど CA の停止に耐えられる。設定で変えられる（下限 1 時間、上限 7 日）

### 8-2. mtls-agent → アプリ

mtls-agent は、新しい出力を書き出します（既存の `output.ca` は自分のルート CA のみのまま変えない）。

| 設定 | 内容 | 使う側 |
| --- | --- | --- |
| `output.trust_bundle` | トラストバンドル（JSON。連携先ごとのルート CA の証明書と範囲、有効期限、署名） | `mtls` ライブラリ |
| `output.federation_dir` | 連携先ごとの PEM（`<連携先>.pem`。その連携先のルート CA だけ）と、その範囲（`<連携先>.domains`） | nginx など（[9-2.](#9-2-mtls-ライブラリ以外nginx-など)） |

- `<連携先>` は、**自分の側で決める識別子**とする。承認の時点で管理者が付ける短い名前（`[a-z0-9-]{1,32}`、連携先の間で一意）で、
  ルート CA の入れ替え（11.）の後も変えない（nginx の設定が参照するファイル名を変えないため）。**相手の申告（`organization` など）はファイル名に使わない**
  （`../` によるパスの書き換えや、同じ名前を名乗る連携先どうしの上書きを防ぐため）
- 停止した連携先・期限が切れたバンドルの連携先のファイルは、**消さずに「どこにもつながらない PEM」に置き換える**。
  これは mtls-agent がその場で作る自己署名の証明書 1 枚で、秘密鍵は作った直後に捨てる（どの証明書もこれにはつながらない）。
  ファイルを消すと、nginx は設定の検査に失敗して reload を行わず、**古い PEM を読み込んだまま連携先を信頼し続ける**ためである
- **自分と連携先のルート CA を混ぜた PEM は出力しない**（それを信頼するだけの設定では S-1・S-2 が守れず、危ない使い方がいちばん簡単になってしまうため）
- 書き出しはこれまでどおり、一時ファイルに書いて rename し、`hooks.post_renew` と同じ仕組みで「バンドルの更新後のコマンド」を実行できる。
  **コマンドが失敗したら、mtls-agent はエラーのログを出し、成功するまで再試行する**（停止が nginx に反映されないまま気づかれない、を防ぐため）。再試行の間隔は、証明書の取得の失敗と同じ指数バックオフ（30 秒〜最大 15 分、揺らぎ付き）とする。
  失敗が続いている間は、`mtls-agent check` が終了コード 1 を返す（監視で拾えるように）

## 9. 接続時の検証

### 9-1. `mtls` ライブラリ

- `Config` に `TrustBundleFile` と `OwnDomains` を追加する。`CAFile`（自分のルート CA）はこれまでどおり必須で、`TrustBundleFile` は
  それに**加えて**連携先を信頼するときに指定する（6-4）
- 自分の範囲は、自分の証明書の fullchain に含まれる**中間 CA の名前制約**から得る（`CAFile` のルートで検証してから使う）。
  `OwnDomains` は、それを**狭める**ためだけに使う（名前制約より広い値は無視し、エラーのログを出す）。
  範囲が得られない（名前制約が無い・空）ときは、`TrustBundleFile` を指定していても**連携先を 1 つも信頼しない**（エラーのログを出す）
- トラストバンドルは、証明書と同じく**再起動なしで読み直す**（`GetConfigForClient` / `VerifyConnection` で、その時点のバンドルを使う）
- バンドルを読むときに確かめること（満たさなければ、そのバンドルは使わず、直前に受け入れたバンドルをその有効期限まで使う）:
  - 署名・エポック・連番・有効期限（8-1）。**有効期限が切れたら、連携先のルートだけを外す**（自分のルートは `CAFile` からなので、
    これまでどおり信頼し続ける）。外したことはエラーのログに出す
  - バンドルの「自分のルートの指紋の一覧」が空でなく、**すべて `CAFile` のルートに含まれる**。満たさなければバンドル全体を拒否する（6-4）
  - 連携先の範囲が、自分の範囲（上記の名前制約。`OwnDomains` で狭めたもの）と重ならない。重なる連携先は外し、エラーのログに出す（6-4）
- 検証の手順:
  1. 通常のチェーンの検証（`CAFile` のルートと、バンドルの連携先のルートを信頼の起点にする）
  2. 自分のルートにつながるチェーンがあれば、これまでどおり受け入れの候補にする
  3. 連携先のルートにつながるチェーンは、証明書が 6-2 の「受け入れる証明書の形」を満たし、DNS 名が**すべて**そのルートの範囲に入るときだけ候補にする。
     複数のチェーンがあれば、いずれかが満たせばよい
  4. `AllowedPeers` で相手の名前を確かめる（これまでどおり）
- クライアント側（接続する側）も同じ検証をする（通常のホスト名の検証に加えて 3. を行う）
- 拒否の理由（範囲の外・ワイルドカード・DNS 名以外の SAN・未承認のルート・期限切れ）をエラーに含め、ログで原因が分かるようにする

### 9-2. `mtls` ライブラリ以外（nginx など）

nginx などは「ルート CA ごとの範囲」や 6-2 の「受け入れる証明書の形」を確かめられません。次のいずれかで補います（運用設計ガイドに手順を書く）。

- **（推奨）** 連携先からの接続を受けるポートを分け、そのポートでは `output.federation_dir/<連携先>.pem`（**その連携先のルート CA だけ**）を信頼し、
  相手の名前（`$ssl_client_s_dn` や SAN）を許可リストで確かめる。自分の組織からの接続は別のポートで、自分のルート CA だけを信頼する
  - 範囲の確認を許可リストで代わりに行うことになるので、**許可リストに書く名前は、その連携先の範囲の内の完全一致の名前に限る**
    （ワイルドカードを書かない。ワイルドカードの証明書を拒否できないため）
  - 連携を停止すると PEM が「どこにもつながらない PEM」に置き換わるので、nginx の reload で信頼も外れる（「バンドルの更新後のコマンド」で
    `nginx -t && systemctl reload nginx` を実行する）
  - 導入時と停止の後には、`nginx -t` が通ること、reload の後に連携先からの接続が拒否されることを確かめる
- `mtls` ライブラリを使った小さな中継（サイドカー）を前に置く

### 9-3. 失効

- 連携先の証明書の失効は、これまでと同じく**短い有効期間**（既定 24 時間）で被害の時間を限る
- 急ぐ場合は、連携そのものを停止する（10.）か、`AllowedPeers` から相手の名前を外す
- （段階 3）連携先の CRL を mtls-ca が取得し、トラストバンドルに失効したシリアルを載せることも検討する

## 10. 連携の停止

- 管理画面（または `mtlsctl federation suspend` / `remove`）で停止する。**停止は 1 人で即時にできる**（承認と違い、守る側の操作なので）
- 停止すると、トラストバンドルの連番を進め、各 mtls-agent が次の確認（既定 1 分以内）で受け取り、アプリが再読み込みした時点で接続を拒否する
- **最悪の場合の遅れ**: mtls-agent と CA の間の通信が妨げられている（または CA が止まっている）と、停止は届かず、手元のバンドルの
  **有効期限（既定 2 日）**まで連携先を信頼し続ける。急ぐ場合は、連携先のサーバの名前を各アプリの `AllowedPeers` から外す（9-3）
  か、nginx などでは信頼している連携先の PEM の設定を外して reload する（ファイルを消すだけでは reload が失敗する。8-2）
- 停止中の連携情報は残し、再開には 7-3・7-4（照合と 2 人の承認）をやり直す
- 連携先の CA の侵害が分かったときの手順（停止 → 連絡 → 影響の調査 → 新しいルートでの再連携）を、運用設計ガイドの事故対応に加える

## 11. ルート CA の入れ替え（連携を切らずに）

ルート CA の鍵はオフラインなので、入れ替えは前もって計画できます。

1. 連携先は、新しいルート CA を作ったら、**古いルート CA で署名した予告**を `mtlsctl root announce` で作る（オフラインの端末で、古いルートの鍵を使う）。
   予告には次を入れる:
   - 新しいルートの指紋と、切り替えの予定日
   - **連携先の識別子**（古いルートの指紋）
   - **範囲**: 古いルートの範囲を**超えない**こと（予告で範囲は広げられない。広げるなら 7-3・7-4 の通常の承認）
   - **予告の有効期限**（例: 90 日）。期限を過ぎた予告は受け付けない（古い予告を再送して、廃止済みのルートを再び入れられないように）
2. その予告と新しいルートの証明書を、連携情報と同じように渡す（段階 3 では CA 同士で自動に取りに行く）
3. 受け取った側は、**今信頼している古いルートで予告の署名を確かめ**、上の内容（識別子・範囲・有効期限）を確かめたうえで、
   新しいルートを「同じ連携先の次のルート」として承認待ちに入れる。署名が正しければ、指紋の照合は不要（古いルートが新しいルートを保証している）。
   承認は 1 人でよい（範囲を広げられないこと・有効期限があることが、この判断の前提）
4. 切り替えの期間中は、新旧両方のルートを同じ範囲で信頼する。連携先は、新しいルートで発行し始めたら古いルートの廃止を知らせ、受け取った側が外す

**古いルートの鍵の侵害が理由の入れ替えには、予告を使いません。** 侵害された鍵で署名した予告は信用できないためです。
その場合は、連携を停止し（10.）、新しいルートで初回と同じ連携（7-1〜7-4。照合と 2 人の承認）をやり直します。

中間 CA の入れ替えは、ルート CA が同じなので、連携先の作業は不要です（これまでどおり）。

## 12. CA 同士の自動の更新（段階 3・任意）

CA 同士が通信できる場合、次を自動にできます。手作業の照合が必要なのは初回だけになります。

- 各 mtls-ca は、連携用の窓口（別のポート、mTLS）で、自分の連携情報・ルートの入れ替えの予告・CRL を公開する
- 窓口への接続は、**すでに承認した連携先の証明書による mTLS** に限る（名前は連携情報に登録する）
- 取得した内容は、署名（ルート CA または中間 CA）を確かめてから使う。範囲の拡大など、**信頼を広げる変更は自動では反映せず、承認待ちにする**
- 定期的に（既定 1 時間）取りに行き、失敗が続いたら管理画面とログで警告する

## 13. 脅威と対策

| 脅威 | 対策 |
| --- | --- |
| 連携先の CA が、自分の組織の名前の証明書を作る（侵害・誤り） | 範囲付きの信頼（6-2）。自分の `allowed_domains` と重なる範囲は承認できない（6-3）。`mtls` ライブラリも重なりを拒否する（6-4） |
| 連携先の CA が、範囲の内の名前で攻撃者に証明書を発行する | 防げない（連携先の責任の範囲）。`AllowedPeers` で相手を最小限にし、連携を停止できるようにする（10.） |
| 連携先の CA が、ワイルドカード・DNS 名以外の SAN・DNS 名の無い証明書を作る | 連携先のルートにつながる証明書は、その形を拒否する（6-2） |
| 初回の交換でルート CA がすり替えられる | 別の経路での指紋の全体の照合（7-3）。照合した指紋の全体を承認の画面で入力させる（7-4） |
| すり替えたファイルの連絡先で、攻撃者と照合させる | 照合の相手は、ファイルとは無関係に前もって知っている連絡先とする（7-3）。ファイルの連絡先は「未検証」と表示し、照合した相手と経路を監査ログに残す（7-2・7-4） |
| 1 人の管理者が不正に連携を承認する | 2 人の承認（7-4）。監査ログ |
| CA サーバ（オンライン）が乗っ取られ、不正なバンドルに署名して配られる | 自分のルートと範囲はバンドルから取らず（範囲はオフラインのルートが署名した中間 CA の名前制約から得る）、ライブラリが重なりを拒否する（6-4）。**ただし、自分の範囲と重ならない「連携先」の追加は防げない**（段階 1 の限界。実装時に `security.md` の「守れないこと」に書く。承認者の鍵での署名は 16. で検討） |
| 古いトラストバンドル（停止前のもの）を、サーバに使わせ続ける | バンドルのエポック・連番・有効期限・署名（8-1）。期限切れで連携先のルートを外す（9-1）。**最悪の場合、停止が届かないまま有効期限（既定 2 日）まで信頼が続く**（10.） |
| CA をバックアップから戻し、連番が戻る | エポックを変え、発行時刻が新しければ受け入れる（8-1） |
| 連携先が乗っ取られたことに気づくのが遅れる | 停止は 1 人で即時（10.）。連絡先を連携情報に含める。有効期限で定期的に見直す |
| 範囲の確かめができないソフト（nginx など）で、範囲の外の名前を受け入れる | ポートを分けて、連携先ごとの PEM だけを信頼する。許可リストは範囲の内の完全一致の名前に限る（9-2） |
| 停止したのに、nginx などが古い PEM を読み込んだまま連携先を信頼し続ける | ファイルを消さずに「どこにもつながらない PEM」に置き換え、reload が成功するようにする。更新後のコマンドの失敗はエラーのログを出して再試行する（8-2） |
| 相手の申告した名前で、出力先の外に書き込まれる・他の連携先のファイルを上書きされる | ファイル名には自分の側で付けた識別子だけを使う（8-2） |
| 連携先が増え、誤った範囲（広すぎる・重なる）で承認する | 承認の画面で、範囲の広さと、自分のドメイン・他の連携先との重なりを機械的に確かめる。起動時とバンドルの作成時にも確かめる（6-3） |
| 古いルートの鍵が侵害され、その鍵で偽の入れ替えの予告が作られる | 予告で範囲は広げられず、有効期限がある（11.）。鍵の侵害が理由の入れ替えでは予告を使わない（11.） |

## 14. 既存の機能への影響

- 連携を使わない構成は、設定を変えずにこれまでどおり動く（`federation` の設定が無ければ、連携の画面・API は無効）
- `mtls` ライブラリの `CAFile` はそのまま使える。`TrustBundleFile` / `OwnDomains` は、連携先を信頼するときに加える新しい選択肢
- **管理画面と ACME は、これまでどおり自分のルート CA だけを信頼する**（連携先の証明書では管理画面に入れず、ACME の相手にもならない）
- mtls-agent の既存の出力（`output.ca` など）の中身は変えない。連携の出力は新しい設定項目だけに書く
- 管理画面の権限（`admin.operators`）と監査ログの仕組みを、連携の操作にも使う
- データベースに連携情報のバケツを追加する（既存のデータの移行は不要）

## 15. 実装の段階

| 段階 | 内容 | これで実現できること |
| --- | --- | --- |
| 1 | `mtls` ライブラリの範囲付きの検証と、バンドルの再読み込み。`mtlsctl federation export / import / approve / suspend`（ファイルで管理）。mtls-agent のバンドルの取得と書き出し。CA の `/federation/bundle` | 手作業の交換で、A と B の連携が動く |
| 2 | 管理画面の「連携」画面（取り込み・照合・2 人の承認・停止・期限の警告）。監査ログ。nginx 向けの運用手順 | 運用者が画面で連携を管理できる |
| 3 | ルート CA の入れ替えの予告（`mtlsctl root announce`）と追従。CA 同士の連携の窓口（自動の更新、CRL の取得） | 初回以外の手作業がなくなる |

各段階で、テストを CI に加えます。段階 1 では少なくとも次を確かめます。

- 範囲の外の名前・ワイルドカードの DNS 名・DNS 名以外の SAN・DNS 名の無い証明書の拒否。複数のチェーンのうち 1 つが条件を満たす場合の受け入れ
- 自分の範囲と重なる連携先の拒否（CA とライブラリの両方）。広すぎる範囲（1 ラベル・パブリックサフィックス）の拒否
- 自分のルートの指紋の一覧が空、または `CAFile` に無い指紋を含むバンドルの拒否。ルートの入れ替え中（`CAFile` に新旧の 2 つ）の受け入れ
- 自分の範囲を中間 CA の名前制約から得ること。名前制約が無いときに連携先を 1 つも信頼しないこと。`OwnDomains` で広げられないこと
- 古いバンドル（連番が戻る）の拒否、エポックが変わったバンドルの受け入れ（発行時刻が新しい場合のみ）
- 期限切れのバンドルで連携先だけが外れ、自分のルートは信頼し続けること
- 停止の反映（`output.federation_dir` のファイルが「どこにもつながらない PEM」に置き換わること）。識別子の書式の検証
- 「バンドルの更新後のコマンド」が失敗したときの再試行

2 つの CA を立てた結合テスト（A のサーバと B のサーバが連携で通ること、範囲の外では通らないこと）も段階 1 で用意します。

## 16. 決めること

実装の前に、次を決める必要があります。

| # | 項目 | 選択肢・推奨 |
| --- | --- | --- |
| 1 | A と B の関係 | **決定済み: 別組織を前提に設計する**（同じ社内にもそのまま使える） |
| 2 | 社内の場合の方式 | **決定済み: 連携版で対応する**。ルート CA を共有してネットワークごとに中間 CA を立てる方式（2. の別案）も、実装なしで使える簡易な選択肢として残す |
| 3 | 2 人の承認 | 既定で必須にするか（推奨: 必須。社内なら設定で外せる） |
| 4 | nginx などへの対応 | 9-2 の「ポートを分ける」手順で足りるか、サイドカーまで用意するか |
| 5 | CA 同士の自動の更新（段階 3） | 必要か。CA 同士の通信を許せるネットワークか |
| 6 | 連携先の失効の扱い | 短い有効期間だけでよいか、CRL の取得まで行うか |
| 7 | 連携の有効期限 | 既定 1 年でよいか |
| 8 | トラストバンドルの有効期限 | 既定 2 日（決定済み）。「停止が届かない最悪の期間」と「CA の停止に耐えられる期間」を兼ねる（8-1・10.） |
| 9 | CA サーバの侵害への備え（段階 2 以降） | 連携の承認の結果（連携先のルートの指紋と範囲）に、承認者の鍵（またはオフラインのルート鍵）での署名を求め、オンラインの中間 CA の鍵だけでは連携先を追加できないようにするか（6-4） |
