# セキュリティ設計

[English](../en/security.md)

mtls_manager が何を守り、何を守れないかをまとめます。導入の前に一読してください。

## 前提

- 全体が**社内のプライベートなネットワーク**で動き、外部のサービスにはつながりません。
- サーバの「身元」は **FQDN** で表します。証明書の DNS 名が、接続相手が誰かを表します。
- 証明書を受け取る資格は、**EAB 鍵（事前の許可）** と **所有確認（http-01 / tls-alpn-01）** の両方で確かめます。

## 守れること

| 脅威 | 対策 |
| --- | --- |
| 社内の任意の機器が、勝手に証明書を取得する | **EAB が必須**。事前に配った鍵が無いとアカウントを作れない |
| EAB 鍵を持つサーバが、他のサーバの名前の証明書を取得する | **EAB 鍵ごとに発行してよい名前を固定**する。加えて、所有確認で CA からその名前に接続して確かめる |
| 社内の DNS が乗っ取られ、所有確認を通される | DNS だけでは足りない。上記のとおり、その名前を許可した EAB 鍵も必要 |
| 中間 CA の鍵が漏れ、社外のドメインの証明書を作られる | 中間 CA に**名前制約（critical）**を付ける。許可したドメインの外の証明書は、検証の時点で拒否される |
| ルート CA の鍵が漏れる | ルート CA の鍵は**オフラインの端末**にだけ置き、CA サーバには置かない |
| 盗まれた証明書を長く使われる | 有効期間を**既定 24 時間**と短くする。EAB 鍵を取り消せば次の更新ができない |
| 署名付きリクエストのリプレイ | 1 回限りの nonce と、`url` ヘッダとリクエスト先の照合（RFC 8555） |
| 他のアカウントの注文・証明書の操作 | すべての操作で、対象がそのアカウントのものかを確かめる |
| 想定外の送信元からの CA の利用 | `allowed_client_cidrs` で送信元を制限できる |
| 同じマシンの他のユーザーによる鍵の読み取り | 秘密鍵・EAB 鍵のファイルが **0600 でなければ起動しない**。鍵は 0600 で書く |
| 証明書の更新中の不整合 | 一時ファイルに書いて rename する。ライブラリは証明書と鍵が対応しないときは直前のものを使い続ける |
| 接続相手の取り違え | ライブラリのサーバ側の設定は、**相手の名前の許可リスト**を必須にする（同じ CA の証明書なら誰でも通る、を既定にしない） |
| 所有確認の誘導 | http-01 はリダイレクトを追わない。環境変数のプロキシを使わない |
| 管理画面への不正なアクセス | ACME とは別のポートで待ち受け、送信元を限れる。ログインはこの CA が発行した証明書による **mTLS** で、名前を `admin.allowed_clients` で限る（パスワードを使わないので、推測・使い回しの心配がない）。すべてのアクセスと拒否を監査ログに残す。失効させた管理者の証明書と、この CA の発行の記録に無い証明書は拒否する。証明書を発行した EAB 鍵が今もその管理者の名前を完全一致で許可していなければ拒否する（鍵の取り消しや、設定を後から広げた場合） |
| サーバ用の EAB 鍵での管理者の証明書の取得 | `admin.allowed_clients` に一致する名前の証明書は、その名前をワイルドカードを使わずに許可した EAB 鍵でだけ発行する（サーバ用の `*.internal.example.com` のような鍵では拒否する）。管理画面からの EAB 鍵の発行でも、管理者の名前と重なるワイルドカードは拒否し、起動時に既存の鍵を警告する |
| 管理画面からの情報の漏えい・改ざん | 鍵や HMAC などの秘密情報は表示しない（EAB 鍵の発行直後に、その HMAC 鍵を 1 回だけ表示する。応答はキャッシュさせず、ログにも出さない）。変更の操作は `admin.operators` の管理者だけに限り、POST のみ・確認必須とする。外部のスクリプトを読み込まない（CSP）。ログは HTML として解釈しないよう表示する。操作の結果の表示はサーバが決めた文言だけで、URL に任意の文言を仕込んで表示させることはできない |
| 管理画面への偽の操作（CSRF） | mTLS ではブラウザが他のサイトからの要求にも証明書を自動で付ける。変更のフォームに管理者ごとのトークン（起動ごとに変わる鍵の HMAC）を埋め込み、`Origin` / `Sec-Fetch-Site` が他のサイトを示す要求を拒否する。CSP の `form-action 'self'` と `frame-ancestors 'none'` で、フォームの送信先の差し替えと埋め込み（クリックジャッキング）を防ぐ |
| 連携先の CA による、自分の組織の名前・範囲の外の名前の証明書（連携版） | 連携先のルート CA は、承認した範囲の名前に限って信頼する。範囲は 2 ラベル以上でパブリックサフィックス不可、自分の範囲・他の連携先と重なれば承認できない。連携先の証明書は、ワイルドカード・DNS 名以外の SAN・DNS 名の無いものを拒否する |
| 連携の初回の交換でのすり替え（連携版） | 指紋の全体を、ファイルとは無関係に前もって知っている連絡先と、別の経路で照合する。申請と承認の両方で指紋の全体を入力し、申請者と承認者は別の名前にする |
| 連携版のクライアントでの中間者（連携版） | 連携版のクライアントは、ホスト名で接続しないと拒否する（IP アドレスでの接続はホスト名を確かめられないため）。サーバ側の `AllowAnyPeer` は自分の組織の相手にだけ効き、連携先の相手は `AllowedPeers` に一致することを必須にする |
| CA サーバの乗っ取りによる、自分の組織の信頼のすり替え（連携版） | 自分のルート CA と範囲はトラストバンドルから取らない（ルートは `CAFile`、範囲はオフラインのルートが署名した中間 CA の名前制約）。バンドルは中間 CA の鍵で署名し、受け取る側が署名・自分のルートの指紋・範囲の重なりを確かめる |
| 古いトラストバンドルの再送・停止の握りつぶし（連携版） | バンドルにエポック・連番・有効期限（既定 2 日）を付け、古いものを拒否する。mtls-agent と `mtls` ライブラリの両方で比べる。期限が切れたら連携先だけを外す |
| 連携先のルート CA の入れ替えでのすり替え（連携版） | 入れ替えの予告は、いま信頼している古いルートの鍵で署名したものだけを受け付ける。予告で範囲は広げられず、有効期限（最大 180 日）があり、停止中の連携先には使えない。鍵の漏えいが理由の入れ替えでは予告を使わない（停止して、初回と同じ照合と 2 人の承認をやり直す） |

## 守れないこと（利用者側で対策が必要）

| 項目 | 内容・推奨 |
| --- | --- |
| CA サーバ自体の侵害 | 中間 CA の鍵で、名前制約の範囲内の任意の証明書を作られる。CA サーバは専用にし、ログインできる人を限り、OS を最新に保つ |
| 証明書を受け取るサーバの侵害 | そのサーバの秘密鍵で、そのサーバとしてふるまわれる。EAB 鍵を取り消し、必要なら失効させる |
| 失効の即時の反映 | v0.x のライブラリと mtls-agent は CRL を確かめない。短い有効期間で被害の時間を限る設計（[運用ガイド](operations.md#証明書を失効させる)） |
| 鍵の保護（HSM / KMS） | v0.x では鍵はファイル（PEM）。CA サーバのディスクの暗号化を推奨。HSM / KMS への対応は今後の予定 |
| EAB 鍵・HMAC の受け渡し | 安全な経路（scp など）で運ぶ。初回の登録後は対象サーバから削除する |
| ルート CA の鍵の保管 | ファイルは暗号化されていない。暗号化した媒体に保管する |
| CA の可用性 | CA が止まると更新できない。24 時間の証明書なら、約 8 時間の停止で期限切れが始まる。監視と、必要なら `cert.validity` の延長を検討する |
| 管理者の端末の侵害 | 管理者の証明書と鍵を盗まれると、管理画面を閲覧される（秘密情報は表示されない）。`admin.operators` の管理者なら、EAB 鍵の発行（新しいサーバの登録）や証明書の失効もされ得る。操作できる人を最小限にする。その管理者の証明書を失効させるか EAB 鍵を取り消すと、すぐに管理画面に入れなくなる。あわせて EAB 鍵を取り消し、`admin.allowed_clients` / `admin.operators` から外す。監査ログで操作を確かめる |
| 時刻のずれ | 証明書の検証は時刻に依存する。全サーバで NTP を使う |
| CA サーバの乗っ取りによる連携先の追加（連携版） | 乗っ取られた CA サーバは、自分の範囲と**重ならない**名前の「連携先」をトラストバンドルに加えられる（段階 1 の限界）。CA サーバへのログインを限り、各サーバの `mtls-agent check` とログ（連携先の一覧）を監視する。アプリの `AllowedPeers` を必要な相手に限る |
| 2 人の承認の本人確認（連携版・CLI） | 管理画面では、操作した管理者の名前をログインの証明書（mTLS）で確かめる。一方、`mtlsctl federation` の `-by` は自己申告で、「申請者と承認者が別の名前」であることしか確かめられない。承認は申請と同じ経路で行うことを必須にしている（経路をまたぐと、同じ人でも別の名前に見えるため）。承認は管理画面で行い、CLI で申請・承認した連携先（画面に「CLI（自己申告）を含む」と出る）は記録を確かめる。CA サーバにログインできる人を限る |
| 連携先の範囲の確認ができないソフト（連携版） | nginx などは連携先ごとの範囲を確かめられない。連携先からの接続を受けるポートを分け、その連携先のルートだけを信頼し、許可リストを完全一致の名前に限る（[運用ガイド](operations.md#別の組織と連携する連携版)） |
| 停止の反映の遅れ（連携版） | CA と各サーバの通信が妨げられると、停止は届かず、最悪はトラストバンドルの有効期限（既定 2 日）まで連携先を信頼し続ける。急ぐ場合はアプリの `AllowedPeers` からも外す |

## 実装上の判断

- **自前の実装の範囲を小さくする**: 署名は Go 標準の `crypto/x509`、JWS の解釈と検証は `go-jose`、データベースは `bbolt`、
  ACME のクライアントは `golang.org/x/crypto/acme` を使います。
- **相互接続の確認**: CI で、Go 標準の ACME クライアントと lego との相互接続を毎回試験しています。
- **既定値は安全側**: EAB 必須、名前制約が無いと中間 CA に署名しない（明示すれば外せる）、`allowed_domains` 必須、
  TLS 1.3 以上（ライブラリ）、ワイルドカード証明書は発行しない。
- **秘密情報をリポジトリに入れない**: テストの鍵もその場で作り、CI の gitleaks で全履歴を検査します。
